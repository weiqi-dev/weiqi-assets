# 公历转农历（llm-tool）

`llm-tool` 扩展点的首个可用工件。装进宿主、人工启用后，对话里的模型就能通过
`llm_tool_call` 工具把公历日期换算成农历；**调用时零网络**（源码已在本地工件里），
每次调用仍在一次性 QuickJS Worker 里执行，库源码不进主线程 JS 环境、不进模型上下文。

## 接口

唯一入口 `call({ method, args })`，`method` 只认白名单里的 `toLunar`：

| 输入 | 形状 | 说明 |
|---|---|---|
| 单日 | `{ "date": "2026-11-17" }` | 严格 `YYYY-MM-DD` |
| 数字单日 | `{ "year": 2026, "month": 11, "day": 17 }` | 等价形式 |
| 范围 | `{ "from": "2026-11-17", "to": "2026-11-19" }` | 含首尾，逐日返回 |

一律返回 `{ from, to, count, days[] }`，单日即 `count=1` 的数组——形状稳定，
模型不用区分「查一天」和「查一段」。`days[]` 每项：

```json
{ "solar": "2026-11-17", "lunar": { "year": 2026, "month": 10, "day": 9, "isLeap": false }, "lunarText": "十月初九" }
```

`lunarText` 用「正月/冬月/腊月」+「初九/廿三」这类中文写法，闰月带「闰」前缀。
不存在的日期（如 `2026-02-30`）、反向范围、早于 `1900-01-31` 的日期一律抛错，
错误由宿主转成工具观察回喂模型，不编造结果。

**范围长度不设人为上限**：循环次数由起止日期的天数差推导，超长范围由宿主既有
`DEFAULT_PLUGIN_LIMITS.maxOutputBytes` 自然截断。资源侧不复制配额数值，也不引入
「最多查多少天」这类无出处的经验常数。

## 数据来源（这条最要紧）

农历不是能从第一性原理在合理代码量内推导的：大小月由朔望月定，闰月由节气定，
都是**天文历法事实**。所以本工件含一张事实表，来源链路如实写在这里，不藏任何数字：

| 出现处 | 来源 | 性质 |
|---|---|---|
| `LUNAR_TABLE` 的 201 行 | 1900–2100 每年「闰哪个月 / 12 个农历月各 29 或 30 天 / 闰月是否 30 天」的公开朔闰事实数值，按可读结构逐行重排 | 天文历法事实，非推导、非拟合 |
| 基准 `1900-01-31` = 农历 1900 年正月初一 | 同一份历法事实的起算点 | 历法事实 |
| 86400000 ms/日、`Date.UTC` 纯换算 | 公历日长定义 / ECMAScript 标准 API | 定义 / 标准 |
| 春节、闰月等校验锚点 | 香港天文台《公历农历对照表》<https://www.hko.gov.hk/en/gts/time/conversion.htm>（1901–2100 逐年可查） | 独立权威核验 |

代码里 `LUNAR_TABLE` 刻意用**可读的 `[公历年, 闰月, '12位月大小串', 闰月是否30天]`**，
而不是常见的十六进制位掩码：每个数都能对照天文台逐年表逐项核验、能争议、能改。
**本文件的换算逻辑、日期解析、接口、中文格式化全部自写**，不含任何第三方库的
实现代码，也没有从验证集扫出来的阈值、系数或门控。

标称支持范围：`1900-01-31` 起，至 2100 农历年末（数据表末尾一行）。早于起点或
超出表末尾会明确报错，不静默外推——事实表没有的年份，不猜测。

### 独立核验锚点（安装自检 `plugin.json.smoke` 用的就是这几个）

| 公历 | 农历 | 核验点 |
|---|---|---|
| `1900-01-31` | 正月初一 | 基准日 |
| `2026-02-17` | 正月初一 | 春节（天文台 2026 对照表可查） |
| `2026-11-17` | 十月初九 | 单日 |
| `2025-07-25` | 闰六月初一 | 2025 闰六月 |
| `2023-03-22` | 闰二月初一 | 2023 闰二月 |
| `1987` 年 | 闰六月、全年 384 天 | 历史闰月 |

这些字段都是确定性的：不提供 `isToday`、节气、生肖等依赖运行时时钟的结果，
安装自检也不会拿非确定性字段做断言。

## 契约来源

| 约束 | 来源 |
|---|---|
| 扩展点 `llm-tool`、spec v1、入口 `call`、hostApi 为空、资源配额 | `weiqi-bot/domain/plugin/types.ts` 的 `LLM_TOOL_SPEC` / `DEFAULT_PLUGIN_LIMITS` |
| `call({method,args})` 的输入只作为 JSON 数据进入沙箱 | `weiqi-bot/infrastructure/plugin-vm/QuickJsExecutor.ts` 的 `__PLUGIN_INPUT__` |
| 方法名只认 `exposes[]` 白名单 | `weiqi-bot/application/plugin/LlmToolKit.ts` |
| 安装前静态预检 + 沙箱试跑 | `weiqi-bot/services/plugin-catalog/PluginCatalogService.ts` |

资源侧**不复制**配额数值：宿主升级 spec 时以宿主为准，本仓库只声明遵守哪个版本。

## 安装形状

与 `ranking` 插件逐字相同：宿主取 `plugin.json` → 按 `code` 取源码 → 静态预检 +
沙箱试跑（跑 `smoke` 里的样例并比对 `expect`）→ 写进工件存储，**默认停用**。
用户在「插件」面板启用后，chat / skill-dev 角色才会看到并调用它。
`catalogRef`（来源 registry URL + 资源 id）用于识别「同一个插件」，远端源码变化
时按钮变「更新」、走 `revise` 保留版本历史。
